# bringup TUIの設計方針

- 用途の入口は「データ記録」に統一し、次の「記録内容」で走行データ／環境記録を選ぶ。
  内部modeとCLIはcollect/environmentを維持し、センサ・録画設定は各modeの設定を使う。
- 用途、評価方式、追跡方式、個別設定を別の選択段階として扱う。
- オフライン評価の方式は保存地図VSLAM、VSLAM＋VGL、新規SLAM、E2E遅延の4つ。
  VO/VIOを各方式の項目名へ展開せず、VSLAMを使う3方式に共通の追跡方式選択を置く。
- 選択した方式に必要な項目だけを表示する。E2E遅延にVSLAM設定を表示しない。
  新規SLAMに保存地図・VGLモデルを要求しない。
- 明示されたCLI指定は優先し、同じ値を対話で聞き直さない。
- 表示整理と実行仕様の変更を混同しない。CLI、launchへの引数、入力検証を維持する。
- 選択順序、明示指定時の省略、VO/VIOの引数伝播をportable testで確認する。
  ROS/GPU/実機の動作確認とは区別する。

## 地図走行の候補推定

- 地図選択はHDMapと上位のcuvslam_mapを含むフォルダーを単位とする。
  フォルダー内HDMapやlane/ラインが一意なら自動採用し、曖昧な場合だけ選ぶ。
- bundleはcuVSLAM地図の内容一致を先に確認し、その中で選択済みInfra解像度に合う候補を優先する。
- モデルはbundleのONNXハッシュ一致を先に確認し、runtime_modelsをsource_modelsより優先する。
  未対応モデルを解像度・名前だけで自動選択しない。
- 候補推定は最終整合性検証を代替しない。明示CLI指定を維持し、自動採用パスを表示する。
- ファイルの移動や前回選択の永続化は行わない。既存の転送フォルダーを利用する。
